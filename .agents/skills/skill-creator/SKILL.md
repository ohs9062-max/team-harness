# 스킬 크리에이터 (Skill Creator)

새로운 스킬을 생성하고 점진적으로 개선하기 위한 스킬입니다.

고수준에서 스킬 생성 프로세스는 다음과 같이 진행됩니다:

- 스킬이 무엇을 해야 하고 대략 어떻게 동작해야 하는지 결정
- 스킬 초안 작성
- 몇 가지 테스트 프롬프트를 만들고, 스킬 접근 권한을 가진 Claude에게 해당 프롬프트를 실행
- 사용자가 정성적 및 정량적으로 결과를 평가하도록 지원
  - 백그라운드에서 실행되는 동안, 아직 없다면 정량적 평가(assertions)를 작성합니다.
  - `eval-viewer/generate_review.py` 스크립트를 사용하여 사용자가 결과를 확인하고 정량적 메트릭을 볼 수 있는 뷰어를 제공합니다.
- 사용자의 결과 평가 피드백을 바탕으로 스킬을 재작성
- 만족할 때까지 반복
- 테스트 세트를 확장하고 더 큰 규모로 다시 시도

이 스킬을 사용할 때 여러분의 역할은 사용자가 이 프로세스의 어느 단계에 있는지 파악하고, 각 단계를 거쳐 발전할 수 있도록 돕는 것입니다.

## 사용자와의 소통 (Communicating with the user)

스킬 크리에이터는 코딩 용어에 대한 친숙도가 매우 다양한 사용자들에 의해 사용될 수 있습니다. 터미널을 처음 열어보는 비개발자부터 컴퓨터에 능숙한 전문가까지 폭넓습니다.

따라서 문맥을 살펴 적절한 어조로 소통하십시오! 기본적으로:
- "평가(evaluation)"나 "벤치마크(benchmark)"는 사용해도 무방합니다.
- "JSON", "assertion(단언/검증 조건)"과 같은 전문 용어는 사용자가 이미 알고 있다는 명확한 신호가 없다면 간단한 설명을 곁들이는 것이 좋습니다.

## 스킬 만들기 (Creating a skill)

### 의도 파악 (Capture Intent)

사용자의 의도를 이해하는 것부터 시작하십시오. 현재 대화에 사용자가 스킬로 변환하고 싶어 하는 워크플로가 이미 포함되어 있을 수 있습니다("이 작업을 스킬로 만들어줘" 등). 그렇다면 대화 기록에서 사용된 도구, 단계 순서, 수정 사항, 관찰된 입출력 형식을 먼저 추출하십시오.

1. 이 스킬을 통해 Claude가 무엇을 할 수 있어야 하는가?
2. 이 스킬은 언제 트리거되어야 하는가? (어떤 사용자 문구/상황)
3. 기대하는 출력 형식은 무엇인가?
4. 스킬 동작 검증을 위한 테스트 케이스를 설정해야 하는가? (파일 변환, 데이터 추출, 코드 생성 등 객관적 검증이 가능한 스킬은 테스트 케이스가 유용함)

### 인터뷰 및 리서치 (Interview and Research)

예외 케이스, 입출력 형식, 예제 파일, 성공 기준, 종속성에 대해 선제적으로 질문하십시오. 이 부분이 명확해질 때까지 테스트 프롬프트 작성을 보류하십시오.

### SKILL.md 작성

인터뷰를 바탕으로 다음 구성 요소를 작성합니다:

- **name**: 스킬 식별자 (영문 소문자, 숫자, 하이픈)
- **description**: 언제 트리거할지, 무엇을 하는지. 이것이 주된 트리거 메커니즘입니다. 스킬이 수행하는 작업과 함께 구체적인 사용 맥락을 반드시 포함하십시오. Claude가 유용한 상황에서도 스킬을 잘 쓰지 않는(undertrigger) 경향이 있으므로, 설명을 다소 적극적이고 명확하게 작성하십시오.
- **compatibility**: 필요한 도구, 종속성 (선택 사항, 거의 불필요)
- **스킬 본문 지침**

### 스킬 작성 가이드 (Skill Writing Guide)

#### 스킬의 구조

```text
skill-name/
├── SKILL.md (필수)
│   ├── YAML frontmatter (name, description 필수)
│   └── 마크다운 지침
└── 번들 리소스 (선택 사항)
    ├── scripts/    - 결정론적/반복적 작업을 위한 실행 코드
    ├── references/ - 필요 시 컨텍스트에 로드되는 문서
    └── assets/     - 출력에 사용되는 템플릿, 아이콘, 폰트 등
```

#### 점진적 공개 (Progressive Disclosure)

스킬은 3단계 로딩 시스템을 사용합니다:
1. **메타데이터** (name + description) - 항상 컨텍스트에 유지 (~100 단어)
2. **SKILL.md 본문** - 스킬이 트리거될 때 컨텍스트에 로드 (500줄 이내 권장)
3. **번들 리소스** - 필요할 때만 로드 (용량 무제한, 스크립트는 로드 없이 직접 실행 가능)

**핵심 패턴:**
- SKILL.md를 500줄 이내로 유지하십시오. 길어지면 계층 구조를 추가하고 모델이 참조할 위치를 안내하십시오.
- 대규모 참조 파일(300줄 이상)은 목차(TOC)를 포함하십시오.

#### 놀람 최소화의 원칙 (Principle of Lack of Surprise)

스킬에는 악성코드나 시스템 보안을 위협하는 코드가 포함되어서는 안 됩니다. 설명된 내용과 일치하지 않는 행동으로 사용자를 놀라게 해서는 안 됩니다.

#### 작성 스타일

강압적인 MUST 남발 대신, **왜 그것이 중요한지 이유를 설명**하십시오. 스킬이 특정 예제에만 과적합(overfitting)되지 않고 일반화될 수 있도록 작성하십시오.

### 테스트 케이스

스킬 초안을 작성한 후, 실제 사용자가 말할 법한 2~3개의 현실적인 테스트 프롬프트를 만드십시오.
테스트 케이스를 `evals/evals.json`에 저장하십시오:

```json
{
  "skill_name": "example-skill",
  "evals": [
    {
      "id": 1,
      "prompt": "사용자의 작업 프롬프트",
      "expected_output": "기대되는 결과 설명",
      "files": []
    }
  ]
}
```

## 테스트 케이스 실행 및 평가

결과는 스킬 디렉터리의 형제 디렉터리로 `<skill-name>-workspace/`에 보관합니다. 이터레이션별(`iteration-1/`, `iteration-2/`), 그리고 테스트 케이스별(`eval-0/`, `eval-1/`)로 디렉터리를 구성합니다.

### 1단계: 모든 실행(스킬 사용 및 베이스라인)을 한 턴에 동시 생성

각 테스트 케이스에 대해 서브에이전트 두 개(스킬 적용 1개, 미적용 1개)를 한 번에 생성하십시오.

- **스킬 적용 실행**: `<workspace>/iteration-<N>/eval-<ID>/with_skill/outputs/`에 저장
- **베이스라인 실행**:
  - 새 스킬 생성 시: 스킬 없음(`without_skill/outputs/`)
  - 기존 스킬 개선 시: 이전 스킬 버전(`old_skill/outputs/`)

각 테스트 케이스에 대해 `eval_metadata.json`을 작성합니다.

### 2단계: 실행이 진행되는 동안 검증 조건(Assertions) 작성

실행 완료를 무작정 기다리지 말고, 각 테스트 케이스에 대한 정량적 단언문(assertions)을 작성하고 사용자에게 설명하십시오.

### 3단계: 실행 완료 시 타이밍 데이터 캡처

서브에이전트 작업 완료 시 반환되는 `total_tokens` 및 `duration_ms`를 각 실행 디렉터리의 `timing.json`에 즉시 기록합니다:

```json
{
  "total_tokens": 84852,
  "duration_ms": 23332,
  "total_duration_seconds": 23.3
}
```

### 4단계: 채점, 집계 및 뷰어 실행

모든 실행이 완료되면:

1. **각 실행 채점** — `agents/grader.md`를 읽는 채점 에이전트를 실행하거나 프로그래밍 방식으로 검증하여 각 실행 디렉터리의 `grading.json`에 저장합니다 (`text`, `passed`, `evidence` 필드 사용).
2. **벤치마크 집계**:
   ```bash
   python -m scripts.aggregate_benchmark <workspace>/iteration-N --skill-name <name>
   ```
3. **분석 수행** — 벤치마크 데이터를 확인하고 이상 패턴 분석 (`agents/analyzer.md` 참조).
4. **리뷰 뷰어 실행**:
   ```bash
   nohup python <skill-creator-path>/eval-viewer/generate_review.py \
     <workspace>/iteration-N \
     --skill-name "my-skill" \
     --benchmark <workspace>/iteration-N/benchmark.json \
     > /dev/null 2>&1 &
   VIEWER_PID=$!
   ```
   (헤드리스 환경에서는 `--static <output_path>`를 사용하여 단독 HTML 파일로 생성)
5. **사용자에게 안내**: 브라우저에서 결과를 확인하고 피드백을 남겨달라고 요청합니다.

### 5단계: 피드백 읽기

사용자가 검토를 마치면 `feedback.json`을 읽고 불만 사항이나 개선 요청을 확인합니다. 뷰어 프로세스를 종료합니다:

```bash
kill $VIEWER_PID 2>/dev/null
```

## 스킬 개선 (Improving the skill)

1. **피드백으로부터 일반화**: 특정 예제에만 맞추는 과적합을 피하고, 백만 번 쓰여도 잘 동작할 수 있도록 근본적인 원리와 패턴을 개선하십시오.
2. **프롬프트를 간결하게 유지**: 불필요하거나 모델의 시간을 낭비하게 만드는 부분을 덜어내십시오.
3. **이유(Why)를 설명**: 명령조의 대문자 MUST/NEVER 대신, 모델이 납득할 수 있는 이유를 설명하십시오.
4. **테스트 케이스 간 중복 작업 포착**: 여러 에이전트가 동일한 헬퍼 스크립트를 직접 작성하고 있다면, 이를 `scripts/`에 번들링하여 스킬에 포함시키십시오.

### 이터레이션 루프

1. 스킬에 개선 사항 적용
2. 모든 테스트 케이스를 새로운 `iteration-<N+1>/` 디렉터리에 재실행
3. 이전 이터레이션을 가리키는 `--previous-workspace` 옵션으로 리뷰어 재실행
4. 사용자 피드백 확인 및 만족할 때까지 반복

## 고급: 블라인드 비교 (Blind comparison)

새 버전이 이전 버전보다 실제로 더 나은지 독립적으로 검증하기 위해 블라인드 A/B 평가를 수행할 수 있습니다. 자세한 내용은 `agents/comparator.md` 및 `agents/analyzer.md`를 참조하십시오.

## 설명 최적화 (Description Optimization)

SKILL.md 프론트매터의 `description`은 Claude가 스킬을 호출할지 결정하는 핵심 요소입니다.

1. **트리거 평가 쿼리 20개 생성**: 트리거되어야 하는 프롬프트 8~10개(구체적이고 현실적인 업무 프롬프트), 트리거되지 않아야 하는 프롬프트 8~10개(키워드는 겹치지만 다른 도구가 필요한 유사 사례)를 작성합니다.
2. **사용자 검토**: `assets/eval_review.html` 템플릿을 통해 사용자 승인을 받습니다.
3. **최적화 루프 실행**:
   ```bash
   python -m scripts.run_loop \
     --eval-set <path-to-trigger-eval.json> \
     --skill-path <path-to-skill> \
     --model <현재 세션의 모델 ID> \
     --max-iterations 5 \
     --verbose
   ```
4. **결과 적용**: 도출된 `best_description`으로 SKILL.md 프론트매터를 갱신합니다.

## 스킬 패키징 (Packaging)

스킬을 배포용 파일(`.skill`)로 묶으려면:

```bash
python -m scripts.package_skill <path/to/skill-folder>
```

생성된 `.skill` 파일을 사용자에게 전달하여 설치할 수 있도록 안내합니다.
