# Engineering Policy

이 문서는 코드를 어떤 개발 원칙으로 구현할 것인가를 정의한다.

모든 AI는 코드 관련 작업 전에 `AGENTS.md`와 이 문서를 모두 확인한다.
`AGENTS.md`는 AI 협업 규칙, 이 문서는 코드 구현 원칙을 다룬다.

목표는 여러 AI가 같은 기준으로 안전하고 일관되게 작업할 수 있는
최소한의 공통 개발 기준이다. AI를 통제하기 위한 규칙 증가가 아니다.

---

## P-001 기존 기능 보존

기존 기능과 새 요구사항이 충돌할 경우:

- 기존 기능을 임의로 삭제하거나 변경하지 않는다.
- 새 기능 구현 때문에 기존 기능 변경이 필요하면
  먼저 충돌 내용과 영향 범위를 사용자에게 보고한다.
- 사용자의 명시적 결정 없이
  기능 삭제, 의미 변경, 기존 동작 제거를 하지 않는다.

## P-002 이름/인터페이스 통일

여러 AI 또는 여러 모듈에서 같은 개념을 다른 이름으로 사용할 수 있다.

이 경우:

- 외부 API, 기존 인터페이스, 기존 데이터 구조를 무리하게 변경하지 않는다.
- 먼저 기존 프로젝트의 공식 명칭과 실제 사용 위치를 확인한다.
- 외부 인터페이스를 유지해야 하면 내부 매핑/변환 계층을 사용한다.
- 여러 이름이 같은 의미라면 내부 표준 명칭을 하나 정한다.
- 단순히 이름이 마음에 들지 않는다는 이유로 전체 rename을 하지 않는다.

## P-003 하드코딩 최소화

변경 가능성이 있는 값은 가능한 한 코드와 분리한다.

- 환경별로 달라지는 값 → `.env`
- 프로젝트 동작 정책, 장비별 설정, 목록, threshold, allowlist, filter, runtime 설정 → `.yaml` 또는 config 파일
- 프로그램 내부에서 절대 변하지 않는 상수 → 코드에 둘 수 있음

모든 값을 설정 파일로 분리하는 과도한 configuration 구조는 만들지 않는다.
목표는 "하드코딩 0"이 아니라 "변경 가능성이 있는 값의 불필요한 하드코딩 최소화"이다.

## P-004 파일 분리 기준

파일을 작게 만들기 위해 무조건 세분화하지 않는다.
응집된 기능은 같은 파일에 둘 수 있다.

하지만 한 파일이 서로 다른 책임을 과도하게 수행하면 분리를 검토한다.
(예: 설정 로딩 + 데이터 수집 + 비즈니스 판단 + API 처리 + DB 접근)

단순히 파일 길이가 길다는 이유만으로 나누지 않는다.
책임이 달라지거나, 의존성이 과도하게 커지거나, 테스트가 어려워질 때 분리한다.

## P-005 단순성 우선

현재 요구사항을 가장 이해하기 쉽고 단순한 구조로 구현한다.

미래에 필요할 수도 있다는 이유만으로
Factory, Adapter, Manager, Registry, 추상 클래스, 복잡한 레이어 등을 미리 추가하지 않는다.

확장이 명백하게 예상되는 지점만 적절한 경계를 둔다.
목표는 "최소 코드"가 아니라 "이해하기 쉬운 최소 복잡도"이다.

## P-006 중복과 공통화

새 기능이 기존 기능과 비슷하다고 해서 무조건 공통화하지 않는다.

- 먼저 기존 코드 재사용 가능성을 조사한다.
- 실제 책임과 동작이 같을 때만 공통화한다.
- 단순히 코드 모양이 비슷하다는 이유로 추상화하지 않는다.
- 반대로 같은 책임을 가진 로직이 여러 위치에서 반복된다면 공통화를 검토한다.

## P-007 AI 간 판단 충돌

설계, 구현, 검수 간 판단이 충돌하는 경우:

- 요구사항에 영향 없는 작은 구현 세부사항은 담당 AI가 판단할 수 있다.
- 다음에 영향을 주면 사용자에게 올린다:
  기능 동작, API, 데이터 구조, 파일 구조, 시스템 구조,
  기존 기능, 보안, 정책, 외부 인터페이스, 작업 범위
- AI끼리 임의로 최종 결정하지 않는다.
- 사용자 판단이 필요한 경우 확정 결과는 `shared/DECISIONS.md`에서 확인한다.

## P-008 기능 제거/동작 변경

새 요구사항 구현을 위해 기존 기능 제거 또는 동작 변경이 필요하면:

- 자동으로 변경하지 않는다.
- 먼저 충돌 원인, 영향을 받는 기능, 가능한 대안, 각 대안의 영향을 제시한다.
- 사용자 결정 후 반영한다.
