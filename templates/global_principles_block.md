## team-harness 전역 원칙 (모든 프로젝트·역할·실행 방식)
- 결과 보고 첫 줄은 `결과: 0`(성공·정상·전부 완료) / `결과: 1`(애매·대기·일부·판정 보류) / `결과: 2`(실패·미달·효과 없음·기각). 확인하지 않은 것을 0으로 보고하지 않는다. WARN·검수 없음은 0이 아니다.
- "효과 없음·원인 아님" 같은 부정 결론은 같은 입력으로 수정 전후 중간 신호를 비교한 근거가 없으면 1(판정 보류)이다. 장시간 학습·실험 전에 수정이 내부 동작을 실제로 바꾸는지 먼저 측정한다.
- 워커·다른 에이전트의 보고를 그대로 믿지 않고 원본(코드·로그·산출물)으로 확인한 뒤 보고한다. 직접 실행한 실험·결론도 같은 기준이다.
- 같은 문제의 독립 검증은 최대 2회. 사실로 확인된 심각한 결함(보안·삭제·데이터 손실·잘못된 성공 보고)만 사용자에게 올리고 나머지는 워커끼리 조율한다.
- 반영은 기능 하나씩 작게: 기능 하나 = 커밋 하나 = 검증 1회. 검증은 기존 대비 회귀·심각 결함만 차단하고 새 기능의 경계 사례는 '알려진 한계'로 기록한다.
- 프로젝트의 `CLAUDE.md`와 `AGENTS.md`는 같은 내용이다. 한쪽을 바꾸면 다른 쪽도 같게 한다(가능하면 한쪽을 다른 쪽의 심볼릭 링크로).
- team-harness 기능을 만들 때는 th 전용으로 만들지 않는다: 가로채기 지점(PATH shim·Claude/Codex hook·git hook·th-launch)이 같은 공통 파이프라인(실행 전/후 단계)을 부르게 하고, 완료 보고에 th 없이 직접 실행한 재현(`## th 밖 재현`)을 넣는다. 정본: team-harness 저장소 `AGENTS.md`.
